# 사용자 피드백 기반 변경 이력

이 문서는 MileDay `v0.1.0`부터 `v0.1.4`까지 사용자 피드백을 바탕으로 수정한 UI/UX 및 동작 개선 사항을 정리한다.

## 기준

- `git tag`로 남아 있는 릴리스 태그는 없다.
- 버전 구분은 `frontend/package.json`의 `version` 변경과 커밋 순서를 기준으로 정리한다.
- `v0.1.3`은 `7108067 perf(goals): 전체 목표 통합 조회 측정 추가`에서 `frontend/package.json` 버전 변경과 성능 측정 결과가 함께 반영된 배포 후보 버전으로 본다.
- `v0.1.4`는 설정창/주요 패널 글자 확대 옵션, 더 작은 캘린더 창 최소 크기 대응, 캘린더 기본 표시 개선, Gemini 전송 동의, 계정 삭제 API를 포함하는 개선 예정 버전으로 본다.

## v0.1.0

### 문제 사항 (피드백)

초기 위젯 UI에서는 마일스톤 완료를 누른 뒤 서버 응답과 재조회가 끝나기 전까지 화면 상태가 흔들릴 수 있었다. 사용자가 보는 관점에서는 방금 완료 처리한 목표나 마일스톤이 잠시 사라지거나, 해당 날짜가 목표 없음 상태처럼 보이는 문제가 있었다.

### 변경 과정

마일스톤 완료 토글 시 서버 응답을 기다린 뒤 전체 데이터를 다시 반영하는 방식에서, 먼저 렌더러 캐시를 갱신하고 실패 시 롤백하는 방식으로 바꿨다. `App.tsx`의 `handleToggleMilestone` 흐름에서 월간/주간 캘린더 캐시와 날짜 상세 캐시를 즉시 갱신하고, API 호출이 실패하면 이전 완료 상태로 되돌리는 구조를 적용했다.

### 변경 결과

마일스톤 완료 클릭 직후 UI가 먼저 반응하게 되었고, 네트워크 지연 중에도 목표/마일스톤 목록이 비어 보이는 현상이 줄었다. 이후 `v0.1.2`에서 목표 완료 상태와 하위 마일스톤 완료 상태 동기화가 추가되면서 완료 처리 정합성도 보강됐다.

## v0.1.1

### 문제 사항 (피드백)

스크롤을 내릴 때 헤더와 달력의 기준 영역이 함께 밀려나 현재 날짜 맥락을 놓치기 쉬웠다. 또한 목표를 한눈에 볼 수 있는 전역 패널이 없어 날짜별 상세 화면을 오가야 했고, 설정에서 글자 크기를 더 작게 조정하고 싶다는 요구도 있었다.

전체 목표 모달에서 목표 색상을 변경해도 이미 생성된 마일스톤과 달력 일부 뷰에는 예전 색상이 남아 있었다. 목표 색상이 사용자 기준으로는 하나의 속성인데, 화면과 DB에서는 부모 목표 색상과 마일스톤 색상이 분리되어 보이는 문제가 있었다.

### 변경 과정

헤더/달력 영역은 스크롤 상황에서도 상단에 고정되도록 CSS를 조정했다. 전체 목표 관리를 위해 `GoalListModal`을 추가하고, 목표 목록, 하위 마일스톤, 다중 삭제 흐름을 한 패널에서 다룰 수 있게 했다.

글자 크기는 설정 패널의 슬라이더와 Electron main process의 정규화 범위를 맞췄다. 기존에는 main process의 `normalizeFontSize()`가 최소값을 10으로 고정하고 있어 UI에서 더 작은 값을 선택해도 저장/재시작 후 10으로 되돌아갔다. 이후 범위를 `1~25px`로 통일했다. 사용자가 말한 "더 작게, 최소 10 수준" 요구는 이 변경에서 더 넓은 범위까지 확장되어 반영됐다.

목표 색상 동기화는 백엔드와 프론트 양쪽에서 보강했다. 백엔드에서는 목표 색상 수정 시 하위 마일스톤 색상도 일괄 갱신하도록 하고, 프론트에서는 달력 렌더링 시 마일스톤 자체 색상보다 부모 목표의 최신 색상을 우선 참조하도록 했다.

### 변경 결과

스크롤 중에도 주요 캘린더 맥락이 유지되고, 전체 목표 모달을 통해 목표와 마일스톤을 한 번에 확인할 수 있게 됐다. 글자 크기 설정은 UI, IPC, 로컬 저장값의 범위가 맞춰져 작은 위젯 화면에서도 더 촘촘한 표시가 가능해졌다.

목표 색상 변경은 달력과 하루 보기에서 즉시 일관되게 보이도록 개선됐다. DB에는 하위 마일스톤 색상도 맞춰 저장되고, 프론트 렌더링은 부모 목표 색상을 단일 진실 원천으로 사용한다.

## v0.1.2

### 문제 사항 (피드백)

사용자 노트북의 물리적 화면 크기, 해상도, Windows 배율, Electron 창 크기 조합에 따라 UI가 압축되거나 잘리는 문제가 있었다. 특히 작은 세로 높이에서는 하루 보기와 설정/생성 패널 접근성이 떨어졌다.

하루 보기 패널이 달력 아래쪽에 위치해 날짜를 누른 뒤 당일 일정을 확인하려면 스크롤해야 하는 흐름도 덜 직관적이었다. 또한 전체 목표 화면은 목표 목록을 가져온 뒤 각 목표별 하위 마일스톤을 순차 조회해 목표 수가 늘어날수록 로딩 비용이 커졌다.

### 변경 과정

반응형 크기 정책을 문서화하고, `px`, `%`, `vh/vw`, `min()`, `clamp()`, `minmax(0, 1fr)`의 역할을 재정리했다. overlay, floating panel, modal처럼 viewport 경계에 맞춰야 하는 요소에는 `vw/vh`와 `clamp()`를 적용하고, 아이콘과 체크박스처럼 고정 크기가 더 안정적인 요소는 `px`를 유지하는 방향으로 정리했다.

날짜 선택 흐름은 선택한 날짜의 하루 보기를 floating panel로 열도록 바꿨다. 사용자는 달력 날짜를 누른 뒤 아래로 스크롤하지 않고 같은 화면 맥락에서 당일 목표와 마일스톤을 확인할 수 있다.

전체 목표 모달은 `GET /goals` 후 목표별 마일스톤 API를 반복 호출하던 구조에서 `GET /goals/with-milestones` 통합 API를 사용하는 구조로 바꿨다. 백엔드는 목표 전체 조회 1회, 마일스톤 전체 조회 1회 후 `goal_id` 기준으로 병합한다. 완료 처리도 RPC로 묶어 목표와 하위 마일스톤의 완료 상태 동기화를 안정화했다.

### 변경 결과

작은 노트북 화면과 고배율 환경에서도 주요 패널이 잘리거나 겹치는 위험이 줄었다. 날짜 클릭 후 당일 일정을 floating panel에서 바로 확인할 수 있어 하루 보기 접근성이 좋아졌다.

전체 목표 조회는 목표별 순차 API 호출을 제거했다. 성능 측정 기준으로 기존 전체 목표 조회 P95 `25,841.67ms`가 통합 API 적용 후 `1,003.54ms`로 줄었다. 목표 완료 처리도 RPC 적용 후 P95 `1,701.87ms`에서 `1,172.69ms`로 개선됐다.

## v0.1.3

### 문제 사항 (피드백)

`v0.1.2`까지 전체 목표 모달과 완료 처리 흐름은 구현됐지만, 피드백을 제품 개선 결과로 설명하려면 실제 성능 개선 폭을 수치로 확인할 필요가 있었다. 특히 전체 목표 화면은 목표 수가 늘어날수록 기존 API 호출 구조의 비용이 커졌기 때문에, 통합 조회 API 적용 후 결과를 별도 측정으로 검증해야 했다.

### 변경 과정

`tests/performance/goals_with_milestones_api_latency.mjs`를 추가해 `GET /goals/with-milestones` 단일 호출의 응답 시간을 측정했다. 기존 `GET /goals` 후 목표별 마일스톤 API를 순차 호출하던 방식과 비교할 수 있도록 ADR 0021의 latency 표도 갱신했다.

또한 `frontend/package.json`과 `frontend/package-lock.json`의 버전을 `0.1.3`으로 올려, 전체 목표 통합 조회와 완료 처리 성능 검증 결과를 다음 배포 후보에 묶었다.

### 변경 결과

전체 목표 조회는 기존 목표별 순차 호출 구조에서 통합 API 1회 호출 구조로 정리됐고, 측정 결과가 문서에 남았다.

| 측정 경로 | 기존 방식 P95 | 개선 후 P95 | 결과 |
|---|---:|---:|---|
| 목표 완료 처리 | 1,701.87ms | 1,172.69ms | RPC 적용 후 응답 시간 감소 |
| 전체 목표 조회 | 25,841.67ms | 1,003.54ms | 통합 조회 API 적용 후 목표 수 증가에 따른 순차 호출 비용 제거 |

`v0.1.3`은 새 UI 기능을 크게 추가한 버전이라기보다, `v0.1.1~v0.1.2`에서 반영한 사용자 피드백 개선 중 전체 목표 조회와 완료 처리의 성능 개선 결과를 측정하고 배포 후보 버전으로 묶은 버전이다.

## v0.1.4

### 문제 사항 (피드백)

설정창과 주요 패널의 글자 크기를 더 크게 볼 수 있는 옵션이 필요했다. 기존에는 설정창 크기만 따로 키우는 방향이었지만, 실제 사용 흐름에서는 하루보기, 일정 추가, 일정 추천, 전체 목표 패널의 텍스트도 함께 커지는 편이 더 일관적이었다.

또한 캘린더 위젯 창의 최소 크기를 더 작게 줄이고 싶다는 요구가 있었다. 다만 너무 작게 줄이면 7열 캘린더, 헤더 버튼, floating panel이 겹치거나 잘릴 수 있어 노트북 해상도와 Windows 배율 차이를 고려한 안정적인 하한값이 필요했다.

캘린더 기본값도 사용자가 기대하는 표시 방식에 맞출 필요가 있었다. 주 시작 요일은 일요일을 기본값으로 두고, 토요일은 일요일/공휴일과 구분되도록 파란색으로 표시해야 했다.

AI 일정 추천은 사용자의 목표 텍스트와 가능 날짜를 Gemini로 전송하므로, 추천 생성 전에 명시적인 전송 동의가 필요했다. 계정 삭제도 앱 안에서 직접 처리할 수 있는 API와 설정창 진입점이 필요했다.

### 변경 과정

로컬 UI 설정에 `작게 | 크게` 옵션을 추가하고, 화면 라벨은 `시스템 글자`로 정리했다. `작게`는 기존 표시 밀도를 유지하고, `크게`는 설정창뿐 아니라 하루보기, 일정 추가, 일정 추천, 전체 목표 패널의 제목, 라벨, 입력값, 버튼, 목표 제목, 메타 텍스트가 함께 커지도록 CSS 변수를 분리했다.

캘린더 창 최소 크기는 기존 `520x380`에서 `420x300`으로 낮췄다. 작은 창에서는 날짜와 목표 색상 점을 우선 보이게 하고, 이벤트 텍스트와 휴일명은 숨겨 캘린더 셀이 깨지지 않도록 했다. Electron window option, CSS `body` 최소 크기, 관련 테스트 기대값을 함께 수정해 창 크기 정책이 어긋나지 않게 했다.

서버 기본 설정과 신규 DB 마이그레이션에서 `week_starts_on` 기본값을 `0`으로 맞췄다. 캘린더 렌더링은 실제 날짜의 `getDay()` 값을 기준으로 일요일과 토요일 클래스를 분리하고, 휴일 클래스는 실제 공휴일 표시 대상에만 적용하도록 정리했다.

사용자 설정 스키마에는 `gemini_data_consent`를 추가했다. 프론트 AI 제안 입력 화면에서 동의 체크박스를 저장하고, `?` 버튼으로 왜 동의가 필요한지와 전송되는 내용을 확인할 수 있게 했다. 프론트와 백엔드는 모두 미동의 상태의 Gemini 일정 추천 요청을 차단한다. 계정 삭제는 Supabase admin client로 현재 access token의 사용자 계정을 삭제하는 `DELETE /auth/account` 경로를 추가하고, 설정창의 계정 삭제 버튼에서 호출하도록 연결했다.

### 변경 결과

사용자는 설정에서 `시스템 글자`를 `작게` 또는 `크게`로 선택할 수 있다. `크게`를 선택하면 설정창, 하루보기, 일정 추가, 일정 추천, 전체 목표 패널의 주요 글자가 더 크게 표시되며, 각 floating panel은 화면 폭을 넘지 않는 범위에서 더 넓게 열린다.

캘린더 위젯은 더 작은 창 크기에서도 사용할 수 있게 됐다. `420x300`, `460x330`, `520x380`, `1366x768` viewport에서 `작게/크게` 상태의 panel overflow와 large 글자 적용을 Chromium 기반 검증 스크립트로 확인했다.

새 계정과 기본 설정은 일요일 시작 캘린더를 사용하고, 토요일은 파란색으로 표시된다. 공휴일/일요일 표시와 토요일 표시가 분리되어 주말 색상 의미가 더 명확해졌다.

Gemini 전송 동의가 꺼져 있으면 AI 일정 추천 생성이 진행되지 않는다. 사용자는 AI 제안 첫 화면에서 동의 여부를 직접 바꾸고, 도움말에서 전송 내용과 미전송 내용을 확인할 수 있다. 계정 삭제는 설정창에서 확인창을 거친 뒤 API를 호출하고, 성공하면 로컬 access token과 앱 상태를 초기화한다.
