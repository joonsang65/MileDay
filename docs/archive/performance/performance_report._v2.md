# MileDay 성능 개선 보고서 v2

> 작성일: 2026-08-14  
> 기준 문서: `docs/performance_report._v1.md`  
> 측정 환경: Electron 개발 서버 + 로컬 FastAPI + 원격 Supabase + Playwright 성능 harness  
> 표본: 플로우별 25회, 총 125회

---

## 1. 요약

v1에서 확인된 핵심 병목은 날짜 선택과 생성/토글 이후 전체 달력 재조회가 반복되면서 `/calendar/month`, `/calendar/date/{date}`, `/settings` 조회가 누적되고, Supabase 연결 오류가 502로 전파되는 구조였다.

v2에서는 월/주 달력 응답을 프론트엔드에서 캐시하고, 날짜 선택 시 이미 받은 달력 데이터에서 하루 보기 데이터를 즉시 구성하도록 변경했다. 목표/마일스톤 생성과 마일스톤 토글은 서버 응답 이후 전체 화면을 다시 불러오는 대신 현재 달력 캐시와 하루 보기 데이터를 직접 갱신한다. 조회 API에는 502/503/504와 일시적 네트워크 오류에 대한 제한적 재시도를 추가했고, 달력 조회 payload와 Supabase 조회 인덱스도 정리했다.

전체 E2E 성공률은 v1 91.2%에서 v2 99.2%로 개선됐다. 날짜 선택 P95는 4,893.93ms에서 98.28ms로 낮아졌고, 목표 생성 P95는 4,964.87ms에서 840.45ms로 낮아졌다. 다만 전체 API 5xx 비율은 v1 4.37%에서 v2 7.91%로 올라갔다. 5xx 대부분은 성공 플로우 안에서 재시도로 복구된 `/settings`, `/calendar/month` GET 요청이지만, 최종 안정성 목표에는 아직 도달하지 못했다.

| 항목 | v1 기준 | v2 현재 | 결과 |
|---|---:|---:|---:|
| 전체 E2E 성공률 | 91.2% | 99.2% | +8.0%p |
| 전체 API 5xx 비율 | 4.37% | 7.91% | 악화 |
| 목표 생성 E2E P95 | 4,964.87ms | 840.45ms | 83.07% 감소 |
| 마일스톤 생성 후 UI 표시 P95 | 8,071.39ms | 2,028.41ms | 74.87% 감소 |
| 마일스톤 토글 시각 반응 P95 | 8,028.72ms | 75.77ms | 99.06% 감소 |
| 설정 변경 후 달력 반영 P95 | 1,332.62ms | 977.24ms | 26.67% 감소 |
| 날짜 선택 E2E P95 | 4,893.93ms | 98.28ms | 97.99% 감소 |

## 4. 개선 명세

### 4.1 날짜 선택 즉시 반영

변경 파일: `frontend/src/App.tsx`

기존 흐름은 날짜를 클릭할 때마다 설정, 월/주 달력, 날짜 상세 조회가 함께 얽혀 있었다. v2에서는 현재 달력 응답의 `days` 데이터에서 선택 날짜를 찾아 `CalendarDateData`를 구성한다.

```text
날짜 클릭
-> selectedDate 변경
-> 현재 calendar.days에서 해당 날짜 데이터 추출
-> 하루 보기 즉시 반영
-> 현재 달력 범위 밖 날짜일 때만 /calendar/date 호출
```

결과적으로 날짜 선택 측정 구간에서 API 호출은 0건이 됐고, P95는 98.28ms로 내려갔다.

### 4.2 월/주 달력 캐시

변경 파일: `frontend/src/App.tsx`

| 모드 | 캐시 키 |
|---|---|
| 월간 | `month:{year}-{month}` |
| 주간 | `week:{start_date}` |

같은 월 또는 같은 주 안에서 이동할 때 기존 응답을 즉시 사용한다. 서버 동기화가 필요한 경우에만 백그라운드 갱신을 수행한다.

### 4.3 최신 요청만 반영

변경 파일: `frontend/src/App.tsx`

빠르게 날짜를 바꾸거나 월/주 이동을 반복할 때 오래된 응답이 늦게 도착해 현재 화면을 덮지 않도록 요청 순서를 추적한다. 현재 선택 날짜와 뷰 모드에 맞지 않는 응답은 상태 반영에서 제외한다.

### 4.4 낙관적 UI 갱신

변경 파일: `frontend/src/App.tsx`

목표/마일스톤 생성, 수정, 삭제, 마일스톤 완료 토글 후 전체 달력을 다시 읽지 않고 현재 캐시와 하루 보기 데이터를 직접 갱신한다. 마일스톤 완료 토글은 클릭 직후 로컬 상태를 먼저 바꾸고, 서버 요청 실패 시 이전 상태로 되돌린다.

```text
클릭
-> 로컬 UI 즉시 변경
-> PATCH /milestones/{id}/complete
-> 성공: 서버 응답으로 캐시 보정
-> 실패: 이전 상태로 rollback
```

### 4.5 조회 API 재시도

변경 파일: `frontend/src/api/client.ts`

| 요청 종류 | 정책 |
|---|---|
| GET | 최대 3회, 100ms -> 300ms backoff |
| POST/PATCH/DELETE | 중복 쓰기 위험 때문에 자동 재시도 없음 |

재시도 대상은 502, 503, 504, 일시적 네트워크 오류다.

### 4.6 백엔드 조회 비용 축소

변경 파일: `backend/app/repositories/calendar.py`

달력 조회에서 `select("*")` 대신 화면과 DTO에 필요한 컬럼만 조회하도록 줄였다.

| 테이블 | 조회 컬럼 |
|---|---|
| `goals` | `id,user_id,title,deadline,is_recurring,recurrence_type,color,created_at,updated_at` |
| `milestones` | `id,goal_id,user_id,title,color,scheduled_date,is_completed,created_at,updated_at,goals(title)` |

### 4.7 휴일 서비스 캐시 유지

변경 파일: `backend/app/services/holiday_service.py`

FastAPI dependency가 요청마다 새 `HolidayService` 인스턴스를 만들지 않도록 `lru_cache`를 적용했다. 월별 휴일 조회 결과가 프로세스 동안 재사용된다.

### 4.8 Supabase 인덱스

변경 파일: `supabase/migrations/202608140001_add_calendar_lookup_indexes.sql`

```sql
create index if not exists idx_goals_user_deadline
on public.goals (user_id, deadline);

create index if not exists idx_milestones_user_scheduled_date
on public.milestones (user_id, scheduled_date);

create index if not exists idx_milestones_user_goal
on public.milestones (user_id, goal_id);
```

## 9. 현재 판단

v2의 주요 성능 개선은 “느린 조회를 더 빨리 기다리는 것”이 아니라 “사용자 조작 직후 불필요한 조회를 제거하는 것”이다. 날짜 선택은 측정 구간 API 호출이 0건이 됐고, 하루 보기 반영은 100ms 이내로 안정화됐다. 목표 생성, 설정 변경, 마일스톤 생성도 1차 목표 범위 안으로 들어왔다.

아직 남은 병목은 조회 API 안정성이다. `/calendar/month`와 `/settings` GET에서 5xx가 반복되며, 재시도 후 성공하더라도 전체 API 5xx 비율은 7.91%로 높다. 다음 개선은 Supabase 연결 안정성, 조회 API timeout/connection pool 설정, `/settings` 중복 호출 제거, 월 조회 경로의 서버 측 캐시 또는 materialized 조회 구조를 우선순위로 잡는 것이 맞다.
