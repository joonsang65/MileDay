# MileDay AI 일정 생성 기능 구현 계획

## 0. 문서 목적

이 문서는 기존 멀티턴 테스트 구조를 실제 MileDay 서비스에 맞게 단순화하고,  
AI 기반 일정 초안 생성 기능과 관련 UI를 단계적으로 구현하기 위한 기준 문서다.

현재 MileDay의 기본 기술 스택은 다음을 기준으로 한다.

- Desktop: Electron
- Frontend: React + TypeScript + Vite
- State: Zustand
- Backend: FastAPI
- Database/Auth: Supabase PostgreSQL + Supabase Auth
- LLM: Gemini API
- 기본 앱 형태: Windows 바탕화면에 띄워두는 캘린더 위젯

---

# 1. LLM 사용 계획

## 1.1 기존 테스트 구조

기존 테스트 코드의 1번 Turn은 항상 `create` 목적의 초기 일정 생성 단계였다.

기존 흐름:

```text
사용자 입력
→ Gemini API 호출
→ structured JSON intent 출력
→ parser
→ plan_items 생성
→ db_payload 생성
→ deterministic validation
→ turn-level judge skip
→ 마지막 turn에서 case-level judge
→ 결과 JSON/report 저장
→ case judge 통과 후 DB write
```

1번 Turn에서는 기존 일정 상태가 없기 때문에 다음과 같이 동작했다.

```text
previous_parsed = None
→ partial update가 아니라 초기 목표 일정 생성
```

기존 구조에서 Gemini가 담당하던 핵심 역할:

- 사용자의 목표 해석
- deadline 해석
- 적절한 세부 작업 분해
- 사용할 일정 slot 선택
- task와 slot 대응
- action=create 판단

---

## 1.2 실제 서비스에서는 멀티턴 수정 기능 제거

실제 MileDay MVP에서는 기존 테스트의 멀티턴 수정 구조를 사용하지 않는다.

AI는 **DB를 직접 수정하지 않고 일정 초안만 생성**한다.

새로운 흐름:

```text
사용자 자연어 요청
→ Gemini API 호출
→ AI 일정 초안 생성
→ 사용자에게 Goal + Milestones 표시
→ 사용자 직접 수정 / 선택 / 삭제 / 추가
→ 클라이언트 및 서버 Validation
→ 최종 DB Payload 생성
→ 사용자 확인
→ DB Write
→ 캘린더 즉시 반영
```

핵심 원칙:

> LLM은 계획 초안 생성까지만 담당하고, DB 스키마 변환과 실제 저장은 deterministic code가 담당한다.

## 1.3 Gemini 출력 구조

Gemini가 기존처럼 DB mutation 구조를 직접 반환할 필요는 없다.

추천 출력 구조:

```json
{
  "goal": {
    "title": "데이터 분석 과제 마무리",
    "deadline": "2026-09-30"
  },
  "milestones": [
    {
      "title": "데이터 수집 및 전처리",
      "scheduled_date": "2026-08-23"
    },
    {
      "title": "탐색적 데이터 분석 수행",
      "scheduled_date": "2026-09-06"
    },
    {
      "title": "모델 학습 및 성능 평가",
      "scheduled_date": "2026-09-20"
    },
    {
      "title": "결과 정리 및 보고서 작성",
      "scheduled_date": "2026-09-27"
    }
  ]
}
```

필요하다면 다음 필드를 추가할 수 있다.

```json
{
  "planning_preference": {
    "intensity": "relaxed",
    "preferred_days": ["weekend"]
  }
}
```

단, 이 값은 UI 표시용이 아니라 내부 scheduling policy에 활용한다.

---

## 1.4 LLM 책임 범위

Gemini가 담당해야 하는 것:

- 사용자 자연어 목표 해석
- 목표 제목 생성
- deadline 해석
- 목표를 수행 가능한 milestone 단위로 분해
- 사용자의 가용 일정과 deadline을 고려하여 날짜 추천
- "여유 있게", "주말 위주", "빠르게" 같은 자연어 선호 해석

Gemini가 담당하지 않아야 하는 것:

- SQL 생성
- Supabase 직접 접근
- goal_id / milestone_id 생성
- DB mutation 수행
- 기존 DB schema에 맞춘 최종 payload 생성
- 실제 저장 여부 결정
- 최종 사용자 확인을 생략한 자동 write

---

## 1.5 기존 selected_slot_ids 구조 수정

기존 테스트에서는 다음처럼 slot id 기반 선택이 중요했다.

```json
{
  "selected_slot_ids": ["S002", "S008", "S014", "S020"]
}
```

실제 앱에서는 LLM이 내부 slot id를 직접 알 필요가 없다.

추천 구조:

```json
{
  "available_dates": [
    {
      "date": "2026-08-23",
      "available_minutes": 240
    },
    {
      "date": "2026-09-06",
      "available_minutes": 300
    }
  ]
}
```

Gemini는 날짜를 반환하고, 서버가 다시 실제 availability를 검증한다.

---

## 1.6 milestone 개수 정책

기존 fixture의 `min_milestones`, `max_milestones`를 제품에 그대로 강제하지 않는다.

정책:

```text
사용자가 milestone 개수를 명시
→ 사용자가 지정한 범위를 우선

"3~5개로 만들어줘"
→ 3~5개 생성

개수를 명시하지 않음
→ 목표 복잡도에 따라 대략 2~6개 생성

매우 단순한 목표
→ 1~2개도 허용
```

중요:

> 테스트를 통과하기 위한 constraint와 실제 사용자 경험을 위한 constraint를 분리한다.

---

## 1.7 일정 강도 해석

사용자 표현:

```text
"너무 빡빡하지 않게"
"여유 있게"
"주말 위주로"
"빨리 끝내고 싶어"
```

등을 단순 텍스트가 아니라 planning preference로 해석한다.

예:

```text
relaxed
- deadline 직전에 몰아넣지 않기
- milestone 간 간격 확보
- 가용 날짜를 모두 사용하지 않기

balanced
- 일정 간 적당한 간격 유지

intensive
- 가능한 빠른 완료를 우선
```

LLM은 preference를 해석하고, 최종 날짜 유효성은 deterministic validation에서 확인한다.

# 2. AI 일정 Draft 구조

프론트엔드에서 AI 응답과 DB Request 타입을 분리한다.

예시:

```ts
type AiScheduleDraft = {
  goal: {
    title: string;
    deadline: string;
  };

  milestones: {
    clientId: string;
    title: string;
    scheduledDate: string;
    selected: boolean;
  }[];
};
```

사용자 수정 후:

```text
AiScheduleDraft
→ validateDraft()
→ buildCreateGoalRequest()
→ POST /goals
→ DB 저장
```

중요:

> AI 응답을 그대로 `/goals` API에 전달하지 않는다.

# 3. Validation 기준

## 3.1 AI 결과 수신 직후

검사 항목:

- Goal title이 비어 있지 않은가
- deadline 파싱이 가능한가
- milestone title이 비어 있지 않은가
- milestone 날짜 파싱이 가능한가
- 모든 AI 추천 milestone이 deadline 이전인가
- AI 추천 날짜가 사용자 availability 안에 있는가
- 선택된 milestone이 최소 1개 이상인가
- 동일한 title + date가 중복되지 않는가

---

## 3.2 사용자가 직접 수정한 이후

사용자가 AI 추천 날짜를 직접 변경할 수 있다.

권장 정책:

```text
AI가 추천한 날짜가 availability 밖
→ 저장 차단

사용자가 직접 날짜를 availability 밖으로 변경
→ 경고 표시
→ 저장은 허용 가능
```

이유:

> 최종 결정권은 사용자에게 둔다.

# 4. AI 생성 실패 UX

Gemini API 호출 실패 시 사용자 입력을 초기화하지 않는다.

표시 예시:

```text
일정 제안에 실패했습니다.
입력한 내용은 그대로 유지됩니다.

[다시 시도]
```

필수 상태:

- idle
- loading
- success
- validation_error
- api_error

사용자가 생성 요청 중 모달을 닫을 수 있도록 한다.

# 6. 다시 제안 기능

`다시 제안` 버튼을 제공한다.

정책 권장:

- 기존 사용자의 자연어 prompt는 유지
- 현재 생성된 draft를 폐기하고 새 draft 생성
- 생성 중 버튼 disable
- 중복 요청 방지
- API 실패 시 기존 draft를 유지

중요:

> 1회 생성 결과를 사용자 수정으로 해결하는 흐름을 기본으로 하고, 다시 제안은 보조 기능으로 둔다.

# 21. Codex 구현 시 주의사항

1. 기존 기능을 먼저 분석하고 무조건 새 구조로 갈아엎지 않는다.
2. DB schema는 기존 MileDay schema를 그대로 사용한다.
3. AI 응답 타입과 DB Request 타입을 분리한다.
4. Gemini 응답을 직접 DB에 저장하지 않는다.
5. AI 결과는 반드시 사용자 확인을 거친다.
6. 기존 goal/milestone CRUD를 최대한 재사용한다.
7. Sidebar 삭제 전 기존 기능 의존성을 확인한다.
8. UI 상태와 server data 상태를 혼합하지 않는다.
9. 모든 API 호출에 loading/error state를 구현한다.
10. Electron window 크기에서 panel overflow가 발생하지 않도록 한다.
11. 작은 창에서도 calendar와 하루 보기의 핵심 정보가 유지되어야 한다.
12. 디자인을 AI 서비스처럼 과도하게 꾸미지 않는다.
13. Sage / Beige 디자인 토큰을 공통 CSS 변수로 먼저 정의한다.

# 22. 최종 사용자 경험

```text
앱 실행

→ 날짜 선택

→ 일정 추가

AI 도움 받기
→ 일정 추천
→ 자연어 입력
→ 초안 생성

→ 필요한 milestone 추가

```

> AI가 사용자를 대신해 일정을 확정하는 것이 아니라,  
> 사용자가 빠르게 결정할 수 있는 좋은 초안을 제공한다.

# 23. 구현 전 확인하면 좋은 항목

Codex가 실제 코드에 반영하기 전에 다음 항목은 현재 repo 기준으로 확인한다.

- 현재 Goal / Milestone DB schema
- 기존 목표 생성 API endpoint
- 기존 milestone 생성 API endpoint
- calendar data fetch 구조
- Zustand store 구조
- 사용자 availability가 현재 어디에 저장되는지
- Gemini 호출 로직의 현재 위치
- 기존 test_api / parser 중 재사용할 부분
- 현재 디자인 token / CSS 방식
- Electron window 최소/기본 크기

위 항목은 문서 작성 자체에는 필수 정보가 아니므로 현재 계획은 그대로 사용할 수 있다.  
다만 Codex가 구현을 시작할 때는 반드시 실제 repo를 먼저 분석한 뒤 경로와 타입을 맞추도록 한다.
