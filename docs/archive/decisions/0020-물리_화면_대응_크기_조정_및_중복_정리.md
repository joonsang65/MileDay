# 물리 화면 대응 크기 조정 및 중복 정의 정리 초안

## 1. 목적

노트북의 물리적 화면 크기, 해상도, 배율 설정, Electron 창 크기 조합에 따라 MileDay 프론트 화면이 압축되거나 잘리는 문제를 줄인다. 특히 작은 노트북 화면, 높은 OS 배율, 낮은 세로 높이에서 달력, 하루 보기, 설정, 생성 패널, 인증 온보딩 화면이 깨지지 않도록 `px`, `%`, `vh/vw`, `min/max`, `clamp()`를 역할별로 재정리한다.

동시에 같은 의미의 기본값, 타입, localStorage key, inline layout 값을 여러 파일에서 반복 정의하는 구조를 줄인다. 크기 정책과 기본 설정의 출처를 명확히 만들어 이후 레이아웃 수정 시 한 파일만 고치면 앱 전체가 같은 기준을 따르도록 한다.

### 적용 범위

- Electron 창 크기 및 resize 동작: `frontend/electron/windowOptions.ts`, `frontend/electron/main.ts`, `frontend/src/App.tsx`, `frontend/src/vite-env.d.ts`
- 앱 본문 레이아웃 CSS: `frontend/src/styles.css`
- 컴포넌트 inline layout style: `GoalListModal.tsx`, `ManualCreatePanel.tsx`, `SettingsPanel.tsx`
- 프론트/백엔드 사용자 설정 기본값: `frontend/src/App.tsx`, `backend/app/services/settings_service.py`
- 인증 화면 언어 저장 key: `frontend/src/App.tsx`, `frontend/src/components/AuthPanel.tsx`

## 2. 중복 내역

### 2.1 로컬 UI 설정 기본값 중복

현재 중복 정의:

| 파일 | 위치 | 값 | 현재 역할 |
| --- | --- | --- | --- |
| `frontend/electron/main.ts` | `DEFAULT_UI_SETTINGS` | `baseFontSize: 12`, `goalFontSize: 13`, `resizeEnabled: false` | Electron main process의 최종 fallback 및 저장값 정규화 기준 |
| `frontend/src/App.tsx` | `DEFAULT_LOCAL_UI_SETTINGS` | `baseFontSize: 12`, `goalFontSize: 13`, `resizeEnabled: false` | React 초기 렌더 fallback |
| `frontend/src/components/SettingsPanel.tsx` | `localUiSettings` props 기본값 | `{ baseFontSize: 12, goalFontSize: 13, resizeEnabled: false }` | prop이 없을 때만 쓰는 SettingsPanel fallback |

최종 적용 흐름:

1. 앱 시작 시 `App.tsx`는 `DEFAULT_LOCAL_UI_SETTINGS`로 초기 렌더링한다.
2. 이후 `window.mileday.uiSettings.get()`을 호출한다.
3. `preload.ts`를 거쳐 `main.ts`의 `ui-settings:get` IPC handler가 실행된다.
4. `main.ts`의 `readUiSettings()`가 로컬 JSON 설정을 읽는다.
5. 저장값이 있으면 저장값이 최종 적용된다.
6. 저장값이 없거나 파싱에 실패하면 `main.ts`의 `DEFAULT_UI_SETTINGS`가 최종 적용된다.

정리 판단:

- 런타임 최종 기준은 `main.ts`의 `DEFAULT_UI_SETTINGS`다.
- `App.tsx`의 값은 초기 렌더 깜빡임 방지용 fallback이므로 main process 기준과 반드시 동기화되어야 한다.
- `SettingsPanel.tsx` 기본값은 현재 `App.tsx`에서 항상 prop을 넘기므로 일반 실행에서는 실질적으로 적용되지 않는다.

개선 방향:

- 프론트 렌더러에서 사용할 `LocalUiSettings` 타입과 기본값을 별도 공유 파일로 분리한다.
- 예: `frontend/src/config/localUiSettings.ts`
- Electron main process와 renderer가 같은 파일을 직접 공유하기 어렵다면, 최소한 값 이름과 테스트를 둔다.
- `SettingsPanel.tsx`의 inline 기본값은 제거하고 `localUiSettings` prop을 필수로 바꾸는 방향을 검토한다.

### 2.2 로컬 UI 설정 타입 중복

현재 중복 정의:

| 파일 | 중복 타입/필드 |
| --- | --- |
| `frontend/electron/main.ts` | `type LocalUiSettings` |
| `frontend/src/App.tsx` | `type LocalUiSettings` |
| `frontend/src/components/SettingsPanel.tsx` | `type LocalUiSettings` |
| `frontend/src/vite-env.d.ts` | `window.mileday.uiSettings` 반환 타입에 `baseFontSize`, `goalFontSize`, `resizeEnabled` 반복 |

문제:

- 새 필드가 추가될 때 4곳을 모두 수정해야 한다.
- `windowBounds`는 main process 타입에는 있지만 renderer 타입에는 없다. 현재 renderer가 직접 쓰지 않기 때문에 동작상 문제는 없지만, 타입 기준이 분산되어 있다.
- `vite-env.d.ts`의 IPC 반환 타입이 별도 객체 형태로 반복되어 구조 변경 시 누락 가능성이 있다.

개선 방향:

- renderer 영역에서는 `frontend/src/types/localUiSettings.ts` 같은 단일 타입을 둔다.
- `SettingsPanel.tsx`, `App.tsx`, `vite-env.d.ts`는 이 타입을 import하거나 동일 타입 alias를 참조한다.
- Electron main process는 Node/Electron 빌드 경계 때문에 import 경로가 애매할 수 있다. 이 경우 `frontend/electron/uiSettings.ts`로 main 전용 타입/기본값/정규화 함수를 모으고, renderer와 값 정합성을 테스트로 보장한다.

### 2.3 ResizeDirection 중복

현재 중복 정의:

| 파일 | 값 |
| --- | --- |
| `frontend/electron/main.ts` | `"n" | "e" | "s" | "w" | "ne" | "nw" | "se" | "sw"` |
| `frontend/src/App.tsx` | `"n" | "e" | "s" | "w" | "ne" | "nw" | "se" | "sw"` |

현재 역할:

- `App.tsx`는 resize handle 렌더링과 pointer event payload 생성에 사용한다.
- `main.ts`는 IPC payload 검증과 실제 창 bounds 계산에 사용한다.

개선 방향:

- renderer에는 `RESIZE_DIRECTIONS` 배열과 타입을 한 파일에 둔다.
- main process에는 같은 배열을 직접 두더라도 `isResizeDirection()` 검증 함수와 테스트를 둔다.
- 가능하면 `frontend/shared/windowResize.ts`처럼 Electron/renderer 양쪽에서 import 가능한 순수 TS 모듈을 만든다.

### 2.4 사용자 설정 기본값 중복

현재 중복 정의:

| 파일 | 값 |
| --- | --- |
| `frontend/src/App.tsx` | `DEFAULT_USER_SETTINGS` |
| `backend/app/services/settings_service.py` | `DEFAULT_SETTINGS` |

현재 값:

```ts
{
  calendar_view: "month",
  theme: "system",
  accent_color: "#4F46E5",
  font_family: "system",
  font_size: 14,
  ai_suggestion: false,
  holiday_display: "normal",
  week_starts_on: 1,
  completed_milestones: true,
  default_goal_color: "#4F46E5",
  default_milestone_color: "#F97316",
  language: "ko",
  timezone: "Asia/Seoul",
}
```

최종 적용 흐름:

1. `App.tsx`는 초기 state로 `DEFAULT_USER_SETTINGS`를 사용한다.
2. 로그인 후 `apiClient.getSettings()`가 `/settings`를 호출한다.
3. 백엔드 `SettingsService.get_settings()`는 DB의 `user_settings` row를 조회한다.
4. row가 있으면 DB 값이 최종 적용된다.
5. row가 없으면 백엔드 `DEFAULT_SETTINGS`로 row를 생성하고 그 값이 최종 적용된다.
6. 로그아웃 시에는 `App.tsx`가 다시 `DEFAULT_USER_SETTINGS`로 state를 초기화한다.

정리 판단:

- 로그인 후 최종 기준은 백엔드 `DEFAULT_SETTINGS` 또는 DB 값이다.
- 프론트 `DEFAULT_USER_SETTINGS`는 초기 렌더와 로그아웃 fallback이다.
- 프론트/백엔드가 다른 언어로 되어 있어 완전한 단일 파일 공유는 어렵지만, 문서화와 테스트로 정합성을 보장해야 한다.

개선 방향:

- 백엔드 `DEFAULT_SETTINGS`를 canonical source로 둔다.
- 프론트 `DEFAULT_USER_SETTINGS`는 "UI fallback copy"임을 주석으로 명시한다.
- API contract test에 프론트 fallback과 백엔드 default의 필드/값 일치 검사를 추가한다.
- 더 나은 방향은 `/settings/defaults` 같은 endpoint 또는 generated schema를 두는 것이지만, 현재 규모에서는 테스트 기반 동기화가 더 가볍다.

### 2.5 인증 화면 언어 key 중복

현재 중복 정의:

| 파일 | 값 |
| --- | --- |
| `frontend/src/App.tsx` | `AUTH_LANGUAGE_KEY = "mileday.auth_language"` |
| `frontend/src/components/AuthPanel.tsx` | `AUTH_LANGUAGE_KEY = "mileday.auth_language"` |

현재 적용 흐름:

1. `App.tsx`의 `getInitialAuthLanguage()`가 localStorage의 `mileday.auth_language`를 읽는다.
2. `"en"`이면 영어, 그 외에는 한국어로 초기화한다.
3. `App.tsx`의 `authLanguage` state가 `AuthPanel`의 `language` prop으로 전달된다.
4. `AuthPanel`에서 언어를 바꾸면 `AuthPanel` 내부에서도 localStorage를 쓰고, `onLanguageChange`로 `App.tsx` state도 갱신한다.

문제:

- 같은 localStorage key를 두 파일이 각자 알고 있다.
- key 변경 시 한쪽만 바뀌면 초기 언어와 저장 언어가 분리될 수 있다.

개선 방향:

- `frontend/src/config/storageKeys.ts`를 만들고 `AUTH_LANGUAGE_KEY`, `ONBOARDING_DISMISSED_KEY`를 모은다.
- `App.tsx`와 `AuthPanel.tsx`는 같은 key를 import한다.
- `getInitialAuthLanguage()`도 한 파일로 분리하면 더 좋다.

## 3. 크기 조정

### 3.1 현재 크기 조정 코드 인벤토리

#### Electron 창 크기

`frontend/electron/windowOptions.ts`

- `WINDOW_SIZE_LIMITS`
  - `minWidth: 520`
  - `minHeight: 380`
  - `maxWidth: 980`
  - `maxHeight: 760`
- 저장된 bounds가 있으면 `width`, `height`를 min/max 범위로 clamp한다.
- 저장된 bounds가 없으면 `getDefaultWindowBounds()`를 쓴다.
- work area가 없으면 기본 `612 x 422`.
- work area가 있으면:
  - `width = clamp(round(workArea.width * 0.36), 560, 760)`
  - `height = clamp(round(workArea.height * 0.48), 422, 640)`

`frontend/electron/main.ts`

- `normalizeWindowBounds()`:
  - 저장된 width/height가 숫자가 아니면 무시한다.
  - 최소값은 `WINDOW_SIZE_LIMITS.minWidth/minHeight`로 보정한다.
- `clampWindowBounds()`:
  - 현재 display work area 안에 창이 들어오도록 `x`, `y`, `width`, `height`를 제한한다.
- `applyResize()`:
  - 동서남북/대각 resize 방향에 따라 bounds를 계산한다.
  - 최소 width/height는 `WINDOW_SIZE_LIMITS`를 사용한다.
- `window-resize:start/update/end` IPC:
  - renderer pointer event를 받아 Electron BrowserWindow bounds를 직접 변경한다.

`frontend/src/App.tsx`

- `RESIZE_DIRECTIONS`로 8개 resize handle을 렌더링한다.
- `WindowResizeHandles`가 pointer event를 받아 `window.mileday.windowResize.start/update/end`를 호출한다.

`frontend/src/styles.css`

- `body`
  - `min-width: 520px`
  - `min-height: 380px`
  - Electron 최소 창 크기와 맞춰져 있다.
- `.window-resize-handle`
  - edge handle: `8px`
  - corner handle: `14px`
- `.app-header::before`
  - drag 영역 보조 크기: `clamp(7px, 1.35vw, 12px)`

조정 아이디어:

- Electron 최소 창 크기와 CSS `body` 최소 크기를 같은 source에서 관리하거나, 최소한 테스트로 동기화한다.
- `520 x 380`은 실제 작은 노트북에서 너무 큰지 확인이 필요하다.
- `maxWidth: 980`, `maxHeight: 760`은 큰 화면에서 위젯이 과도하게 커지지 않게 하는 역할이므로 유지하되, 노트북 고배율 환경에서 work area 기반 max clamp가 제대로 작동하는지 확인한다.

#### 앱 shell과 주요 레이아웃

`frontend/src/styles.css`

- `.planner-workspace`

- `.primary-pane`
  - `height: clamp(320px, 70vh, 800px)`
- `.side-pane`
  - `gap: 11px`
  - `padding-right: 2px`
  - `padding-bottom: 14px`
- `.floating-layer`
  - `padding: 43px 8px 8px`
- `.floating-layer.center`
  - `padding: 16px`
- `.floating-panel`
  - `width: min(clamp(304px, 42vw, 376px), calc(100vw - 16px))`
  - `max-height: calc(100vh - 52px)`
- `.floating-panel.plain`
  - `width: min(clamp(430px, 66vw, 620px), calc(100vw - 33px))`
  - `max-height: calc(100vh - 33px)`

  - `width: 95vw`
  - `max-width: 1000px`

조정 아이디어:

- fixed `px`는 터치/클릭 target, 최소 readable spacing, icon size에 사용한다.
- `%`는 부모 기준으로 꽉 차야 하는 row, input, list에 사용한다.
- `vh/vw`는 overlay, floating panel, onboarding처럼 viewport 경계에 맞춰야 하는 요소에 사용한다.
- `clamp()`는 "최소 사용 가능 크기 - 이상적 비율 - 최대 크기"가 모두 필요한 shell padding, panel width, calendar height, onboarding layout에 사용한다.

### 3.2 단위 사용 원칙

| 단위/함수 | 사용할 곳 | 피할 곳 |
| --- | --- | --- |
| `px` | icon, checkbox, drag handle, 최소 터치 target, border, 작은 gap, form control height | viewport에 따라 줄어야 하는 panel width/height |
| `%` | 부모 폭을 채우는 input/list/button, grid 내부 flexible 영역 | 부모 크기가 불안정한 overlay의 최상위 width |
| `vw` | viewport 폭에 맞춰 줄어야 하는 modal/floating panel, shell padding 보조값 | 텍스트 크기 직접 조절 |
| `vh` | viewport 높이에 맞춰 제한해야 하는 panel max-height, primary pane 후보 높이 | 내용 고유 높이를 완전히 무시하는 고정 height |
| `min()` | viewport보다 커지면 안 되는 panel width/height | min/max/ideal 값이 모두 필요한 경우 |
| `max()` | 최소 영역을 보장해야 하는 계산 | 무조건 큰 값을 강제해 작은 화면 overflow를 만드는 곳 |
| `clamp()` | 최소/이상/최대 크기를 모두 정의해야 하는 padding, panel width, column width, calendar height | 고정되어야 하는 icon size |
| `minmax(0, 1fr)` | grid overflow 방지, 긴 텍스트 ellipsis가 필요한 column | fixed control width가 필요한 column |

## 추가 기준: 반응형 크기 정책

이 문서에 따라 진행하는 반응형 크기 조정 작업은 아래 기준을 반드시 따른다. 목표는 현재 UI를 `1920x1080` 해상도 기준 디자인으로 유지하면서, 다른 노트북과 모니터에서도 UI가 겹치거나 잘리지 않도록 주요 크기 값을 `clamp()` 중심으로 정리하는 것이다.

### 기준 해상도

- 최소 지원 해상도: `1280x720`
- 주요 소형 노트북 테스트 해상도: `1366x768`
- 기준 해상도: `1920x1080`
- 16:10 노트북 테스트 해상도: `1920x1200`
- 최대 기준 해상도: `2560x1600`
- `2560x1600` 이상에서도 UI가 과도하게 커지지 않도록 최대값을 제한한다.

### 적용 원칙

- 현재 `1920x1080`에서의 UI 크기와 비율을 기준값으로 삼는다.
- `1920x1080` 화면에서 현재 디자인이 크게 변하지 않는 것을 가장 중요한 기준으로 한다.
- 화면 크기에 따라 변해야 하는 패널 높이/너비, 여백, `gap`, `padding`, 모달 크기, 버튼 크기, 글자 크기에 `clamp()`를 적용한다.
- `vw`, `vh`만 단독으로 사용하는 방식은 지양하고, `최소값(px) + 화면 비율 기반 값 + 최대값(px)` 구조를 사용한다.
- `1280x720`에서도 요소가 겹치거나 잘리지 않고 핵심 기능을 사용할 수 있어야 한다.
- `2560x1600` 이상에서는 요소가 계속 커지지 않도록 최대 크기를 제한한다.
- 모든 고정 `px` 값을 무조건 변경하지 않는다. icon, border, checkbox, color swatch, drag handle처럼 고정 크기가 더 안정적인 요소는 기존 값을 유지한다.
- 버튼, input, select 등 조작 요소는 작은 화면에서도 클릭하기 어려울 정도로 축소하지 않는다.
- 글자 크기도 `clamp()`를 적용할 수 있으나, 작은 화면에서 가독성이 떨어질 정도로 축소하지 않는다.
- 본문 텍스트는 원칙적으로 최소 `12px` 이하로 내려가지 않도록 한다. 단, badge, metric, 보조 metadata처럼 본문이 아닌 요소는 기존 UI 밀도와 가독성을 함께 검토해 예외로 둘 수 있다.
- Windows `125%`와 `150%` 디스플레이 배율에서도 레이아웃이 깨지지 않는지 함께 확인한다.

### clamp() 산정 방식

`clamp(min, preferred, max)`를 적용할 때는 다음 순서로 값을 산정한다.

1. 기준 해상도 `1920x1080`에서 현재 적용되고 있는 크기를 기준값으로 잡는다.
2. `preferred` 값은 기준 해상도에서 기존 크기와 거의 같은 값이 나오도록 `vw`, `vh`, 또는 둘을 포함한 계산식으로 정한다.
3. `min` 값은 `1280x720`과 `1366x768`에서 요소가 겹치거나 잘리지 않는 최소 사용 가능 크기로 정한다.
4. `max` 값은 `2560x1600` 이상에서 UI가 과도하게 커지지 않는 상한으로 정한다.
5. 적용 후 `1920x1080`에서 기존 크기와 큰 차이가 나면 `preferred` 값을 다시 조정한다.

예시:

```css
.some-panel {
  width: clamp(304px, 19.6vw, 376px);
}
```

위 예시는 `1920px` 기준에서 `19.6vw`가 약 `376px`이 되므로 기존 `1920x1080` 디자인의 최대 크기를 유지하면서, 작은 화면에서는 `304px` 아래로 줄어들지 않도록 제한한다.

### 검증 기준

반응형 크기 정책을 적용한 변경은 최소한 다음 조건을 확인한다.

- `1280x720`: 핵심 기능 접근 가능, 주요 버튼/input/modal이 잘리지 않음
- `1366x768`: 소형 노트북에서 calendar, TodayList, SettingsPanel, GoalListModal이 겹치지 않음
- `1920x1080`: 기존 기준 디자인과 크기/비율이 크게 달라지지 않음
- `1920x1200`: 16:10 노트북에서 세로 여백이 과도하거나 부족하지 않음
- `2560x1600`: UI가 계속 확대되지 않고 max 값 안에서 안정적으로 유지됨
- Windows `125%` / `150%` 배율: 글자, 버튼, input, modal scroll 영역이 깨지지 않음

### 우선 적용 대상

우선적으로 `clamp()` 적용을 검토할 대상은 다음과 같다.

- app shell padding과 workspace gap
- `.primary-pane` 높이
- floating panel과 modal width/max-height
- calendar cell padding과 주요 panel 높이
- `.manual-milestone-list li`, `.draft-list li`, `.day-view-summary`처럼 작은 화면에서 column 폭이 깨질 수 있는 grid column
- quick action popover width
- SettingsPanel, GoalListModal, ManualCreatePanel의 버튼/input 크기 중 viewport에 따라 조정이 필요한 값
