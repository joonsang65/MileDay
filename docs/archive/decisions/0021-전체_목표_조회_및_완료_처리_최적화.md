# 전체 목표 조회 및 완료 처리 최적화

## 배경 (Context)

전체 목표 화면은 목표 목록을 가져온 뒤 각 목표마다 하위 마일스톤을 별도 API로 조회하고 있었다. 목표 수가 늘어나면 `1 + 목표 수`만큼 HTTP 요청과 DB 조회가 발생하므로, 화면 로딩 비용이 목표 개수에 비례해 커지는 구조였다.

또한 목표/마일스톤 완료 처리는 백엔드 서비스에서 여러 쿼리를 순차 실행했다. 목표 완료 시 부모 목표와 하위 마일스톤 상태를 함께 변경해야 하고, 마일스톤 완료 시 부모 목표 완료 상태를 다시 계산해야 하므로 중간 실패 시 정합성 관리 부담이 있었다.

## 의사결정 (Decision)

세 가지 최적화를 순서대로 적용한다.

### 1. 전체 목표+마일스톤 별도 API 추가

`GET /goals/with-milestones`를 추가한다.

이 API는 기존 `/goals` 응답 계약을 변경하지 않고, 전체 목표 화면에 필요한 중첩 데이터를 별도 응답으로 제공한다. 라우터 경로는 `/goals/{goal_id}`보다 먼저 선언해 `with-milestones`가 목표 ID로 해석되지 않도록 한다.

### 2. 완료 처리 RPC 함수 도입

다음 PostgreSQL 함수를 추가한다.

- `public.complete_goal_with_milestones(p_goal_id, p_user_id, p_is_completed)`
- `public.complete_milestone_and_sync_goal(p_milestone_id, p_user_id, p_is_completed)`

백엔드는 Supabase `rpc()` 호출로 완료 처리를 수행한다. 함수는 `user_id` 조건으로 소유권을 제한하고, 변경된 row가 없으면 기존 API와 동일하게 404 계열 예외로 매핑한다.

### 3. 전체 목표 조회를 2-query 병합으로 최적화

`/goals/with-milestones` 내부 구현은 다음 방식으로 고정한다.

```text
1. goals 전체 조회
2. milestones 전체 조회
3. 백엔드에서 goal_id 기준으로 마일스톤을 그룹화
4. 목표 row에 milestones 배열을 붙여 반환
```

필터나 pagination으로 데이터 범위를 줄이는 방식은 이번 범위에서 제외한다. 목적은 전체 데이터를 유지하면서 요청 수와 DB 왕복 구조를 안정화하는 것이다.

## 결과 및 영향 (Consequences)

전체 목표 화면은 목표별 마일스톤 개별 요청을 제거하고 `GET /goals/with-milestones` 한 번으로 필요한 데이터를 가져온다. 서버 내부 DB 조회는 목표 1회, 마일스톤 1회로 고정된다.

완료 토글은 DB RPC 함수로 묶여 백엔드 애플리케이션 레벨의 다중 조회/수정 흐름을 줄인다. 목표 완료는 부모 목표와 하위 마일스톤을 같은 함수에서 처리하고, 마일스톤 완료는 부모 목표 완료 상태 재계산을 같은 함수에서 처리한다.

월간 캘린더 캐시는 기존처럼 장애 대응 레벨로 유지한다. 정상 요청에서 DB 부하를 줄이는 read-through 캐시로 확장하지 않는다.

## Latency 비교

목표 완료 처리와 전체 목표 조회는 각각 RPC 도입, 통합 API 도입 전후를 동일한 API 응답 P95 기준으로 비교한다.

| 측정 경로 | 기존 호출 방식 | 최적화 후 호출 방식 | 기존 latency | 최적화 후 latency | 측정 기준 | 출처 |
|---|---|---|---:|---:|---|---|
| 목표 완료 처리 | 백엔드 서비스에서 목표 확인, 목표 업데이트, 하위 마일스톤 조회/업데이트를 순차 처리 | `complete_goal_with_milestones` RPC 1회 호출 | 1,701.87ms | 1,172.69ms | API 응답 P95 | 기존: `logs/perf/goal-complete-api-20260827-110620-KST.jsonl`, RPC: `logs/perf/goal-complete-api-20260827-112338-KST.jsonl` |
| 전체 목표 조회 | `GET /goals` 1회 후 목표 25개에 대해 하위 마일스톤 API 25회 순차 호출 | `GET /goals/with-milestones` 1회 호출 | 25,841.67ms | 1,003.54ms | API 응답 P95 | 기존: `logs/perf/goals-legacy-list-api-20260827-110711-KST.jsonl`, 통합: `logs/perf/goals-with-milestones-api-20260827-112439-KST.jsonl` |

측정 조건 메모:

- 목표 완료 처리: 기존/RPC 모두 25회 반복, 실패 0건 기준이다.
- 전체 목표 조회: 기존 측정은 25개 목표에 대해 26회 요청을 순차 실행했다. 통합 API 측정은 DB에 누적된 50개 목표를 1회 요청으로 조회했다.
- 통합 API 측정 시 마일스톤 수는 0개였으므로, 마일스톤이 많은 실제 데이터에서는 payload 크기에 따라 latency가 달라질 수 있다.

|---|---|---|---|---:|
| 1 | 전체 목표+마일스톤 별도 API 추가 | `GET /goals/with-milestones`와 중첩 응답 스키마 추가 | 라우터/서비스 테스트 통과 | 96% |
| 2 | RPC 함수 도입 | 목표 완료, 마일스톤 완료 동기화 RPC migration 및 레포지토리 연동 추가 | 레포지토리/서비스/migration 테스트 통과 | 95% |
| 3 | 전체 목표 조회 2-query 병합 | 목표 전체 1회, 마일스톤 전체 1회 조회 후 `goal_id` 병합 | 백엔드 전체 테스트 및 프론트 타입체크 통과 | 96% |

## 검증 메모

- 백엔드 전체 테스트: `110 passed, 1 deselected`, coverage `93.45%`
- 프론트 타입체크: `npx tsc --noEmit` 통과
- 프론트 Vitest 관련 테스트는 현재 실행 환경에서 `vite.config.ts` 로딩 중 상위 디렉터리 접근 제한으로 실행하지 못했다. 권한 승격 재시도도 환경 정책상 거부되었다.
- 원격 Supabase DB 반영: `supabase db push`는 CLI가 사용자 홈의 `.supabase` 텔레메트리 파일을 쓰려다 샌드박스 권한으로 실패했다. 권한 승격 재시도도 환경 정책상 거부되어, 실제 원격 DB 적용은 로컬 터미널에서 별도 실행이 필요하다.
