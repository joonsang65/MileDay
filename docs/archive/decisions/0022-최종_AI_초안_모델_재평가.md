# ADR 0022. 최종 AI 초안 모델 재평가

## 상태

Measured once. 10개 제품형 케이스로 1차 자동 측정을 수행했다.

## 배경

기존 모델 평가는 자연어 일정 수정, 멀티턴 상태 보존, DB payload 생성까지 포함한 구조를 기준으로 했다. 현재 제품 기능은 이보다 좁다. LLM은 사용자의 자연어 목표를 해석해 편집 가능한 일정 초안을 만들고, 날짜 제약, availability, 중복 검증, 저장 payload, DB write는 애플리케이션 코드가 책임진다.

따라서 `SLM이 부족해서 API로 전환했다`가 아니라, 최종 책임 경계에서 어떤 모델이 사용자 수정 비용, 지연, 비용의 균형을 맞추는지 다시 봐야 한다.

## 비교 대상

| 대상 | 기준 |
|---|---|
| Local SLM | Ollama 기반 로컬 후보. 기존 후보는 `granite4.1:3b`를 우선 비교 대상으로 둔다. |
| API LLM | 현재 제품 기본값인 `gemini-3.5-flash-lite` |

## 평가 범위

- 입력: 사용자의 자연어 목표, `today`, `timezone`, `availability[]`
- 출력: `goal`, `milestones[]`, `planning_preference`
- 제외: 기존 일정 직접 수정, 자동 리스케줄링, DB mutation, SQL, 외부 캘린더 연동
- 검증: `validate_ai_schedule_draft()`의 deterministic validation 결과를 우선 사용한다.

## 테스트셋 기준

최소 10개 제품형 케이스로 시작한다.

| 케이스 | 확인 포인트 |
|---|---|
| 기본 마감일 목표 | 저장 가능한 초안 생성 |
| 주말 선호 | preferred days 반영 |
| 평일 선호 | availability와 요일 제약 동시 반영 |
| 촉박한 마감 | 과도한 milestone 분해 방지 |
| 여유 있는 마감 | relaxed/balanced/intensive 차이 |
| sparse availability | 사용 가능 날짜 밖 배치 방지 |
| milestone 개수 지정 | 요청한 개수와 실제 분해 일치 |
| 모호한 날짜 표현 | 마감일 해석 안정성 |
| 불가능한 요청 | 잘못된 확정 대신 validation 실패 유도 |
| 구어체 한국어 요청 | 자연어 의도 해석 품질 |

## 측정 지표

| 지표 | 측정 방식 |
|---|---|
| Draft validity | schema parse 성공 및 `validation.is_valid=true` 비율 |
| Constraint pass | deadline, availability, duplicate 관련 failure code가 없는 비율 |
| Preference adherence | 선호 강도와 선호 요일이 반영된 비율. 필요 시 수동 판정 병행 |
| Avg edit count | 저장 전 사람이 수정해야 하는 제목, 날짜, 삭제, 추가 횟수 평균 |
| Latency | 요청부터 응답 수신까지의 평균, p50, p95 |
| Cost | API token 기준 예상 비용. 로컬 SLM은 로컬 실행 비용으로 별도 표기 |

## 결과 표

2026-08-31 기준 1차 측정 결과다. 동일한 prompt builder, response schema, parser, validator를 사용했다. Avg edit count는 생성 초안을 보고 LLM-as-judge 방식으로 판정했다.

| Model | Draft validity | Constraint pass | Preference adherence | Avg edit count | Latency | Cost | Decision |
|---|---:|---:|---:|---:|---:|---:|---|
| Local SLM (`granite4.1:3b`) | 8/10 | 8/10 | 7/10 | 4.7 | avg 4.183s | 로컬 실행 | 후보 유지, 기본값 보류 |
| Gemini Flash Lite | 10/10 | 10/10 | 10/10 | 0.2 | avg 2.598s | API token 기준 별도 산정 | 제품 기본값 유지 |

## Avg edit count 판정 기준

LLM-as-judge는 사용자가 저장하기 전 최소 수정 횟수를 센다. 목표 제목 수정, 마일스톤 제목 수정, 날짜 변경, 마일스톤 삭제, 마일스톤 추가를 각각 1회로 계산한다. Validation을 통과해도 제목이 깨졌거나 요청 의도와 다른 작업이면 수정 대상으로 본다.

## 관찰된 실패 유형

세부 taxonomy 기준은 [../../ai.md](../../ai.md)의 Failure taxonomy를 따른다.

| 유형 | 관찰 |
|---|---|
| 제목 품질 실패 | Local SLM에서 의미가 불명확한 한국어 제목이 반복됐다. |
| 제약 위반 | Local SLM에서 `MILESTONE_AFTER_DEADLINE`, `MILESTONE_OUTSIDE_AVAILABILITY`가 발생했다. |
| 선호 불일치 | Local SLM에서 주말/요일 선호와 실제 배치가 어긋난 케이스가 있었다. |
| 과분해 | Local SLM의 weekday 케이스에서 11개 milestone이 생성돼 `MILESTONE_COUNT_HIGH`가 발생했다. |
| 보정 필요 요청 | 과거 마감 요청은 Gemini도 저장 가능한 catch-up 초안으로 바꿨지만, 사용자 의도 확인이 필요한 케이스다. |

## 1차 해석

자동 validation만 보면 Local SLM도 일부 케이스에서 저장 가능한 초안을 만들지만, LLM-as-judge 기준으로는 한국어 제목 품질과 요청 의도 반영에서 수정 비용이 크다. 특히 validation이 잡지 못하는 제목 품질 실패가 반복됐다.

Gemini Flash Lite는 validation, 선호 반영, edit count에서 우세했다. 1개 케이스에서 latency spike가 있었지만 평균 지연도 Local SLM보다 낮았다. 현재 제품 기본값은 Gemini Flash Lite 유지가 합리적이고, Local SLM은 비용/프라이버시 요구가 커질 때 재검토할 후보로 둔다.

## 해석 기준

- SLM도 충분하면: 현재 책임 경계에서는 local inference 전환 가능성을 후속 선택지로 유지한다.
- Gemini가 명확히 우세하면: API 비용을 지불하더라도 사용자 수정 횟수와 제약 준수에서 이득이 있음을 근거로 유지한다.
- 두 모델 모두 실패가 크면: 모델 교체보다 prompt, schema, validator, UX confirmation 경계를 먼저 조정한다.

## 현재 실행 메모

- 로컬 Ollama 후보는 설치 상태를 확인했다. `granite4.1:3b`, `ministral-3:3b`, `qwen3.5:4b`, `ingu627/exaone4.0:1.2b`가 설치돼 있어 1차 비교를 위한 추가 설치는 필요 없다.
- Gemini API 호출은 사용자 승인 후 수행했다.
- 이번 측정은 token usage를 기록하지 않았다.
