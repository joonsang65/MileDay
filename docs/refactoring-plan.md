# MileDay 리팩토링 실행 순서

변경 전 동작을 테스트로 남긴 뒤 데스크톱 캘린더부터 정리한다. 모바일은 테스트와 빌드를 CI에 연결한 뒤 화면을 옮긴다. 변경 근거와 현재 폴더 구조는 [리팩토링 검토](refactoring-review.md)에 있다.

완료 기준은 데스크톱과 모바일의 사용자 흐름, API의 요청·응답, 기존 저장 데이터의 읽기 동작이 변경 전과 같은 것이다. 저장 키·형식과 DB 스키마는 유지한다. 계획의 범위는 기준선 확인 한 단계와 구현 일곱 단계다. 캐시와 공통 API 타입에는 변경 전후 비교 테스트가 필요하다. 순수 함수와 라우터 파일명 이동은 기존 테스트와 변경 범위 확인으로 충분하다.

## 0. 기준선 확보

작업 브랜치의 시작 커밋과 아래 결과를 기록한다. 캐시 응답 순서, 모바일 화면 동작, API 응답 비교처럼 기존 테스트에 빈 곳은 해당 코드를 옮기기 전에 보강한다. 기준선에서 실패하면 먼저 기존 결함인지 확인하고 해당 동작의 변경 여부를 별도로 결정한다.

| 위치 | 기준선 명령 |
|---|---|
| 저장소 루트 | `python -m pytest -q` |
| `frontend/` | `npm test`, `npm run build` |
| `mobile-pwa/` | `npm test`, `npm run build` |

두 앱의 전체 빌드와 모바일 브라우저 흐름을 기준선에서 확인한다. 명령의 종료 상태와 테스트 결과를 실행 로그로 남긴다. 2단계의 지연 응답, 4단계의 모바일 브라우저 흐름, 5~7단계의 응답 비교도 각 코드 변경 전에 기준 결과를 확보한다.

## 1. 데스크톱 캘린더 순수 함수 이동

`App.tsx`에서 목표와 마일스톤의 변경을 달력과 날짜 상세 데이터에 반영하는 순수 함수만 옮긴다. 기존 호출부, 호출 순서, 함수 입출력을 유지한다. 월·주 보기, 날짜 상세, 오늘 패널에 같은 변경이 반영되고, 실패한 변경만 되돌아가는지 확인한다. [갱신 함수](../frontend/src/calendar/calendarUpdates.ts#L32) · [앱 회귀 테스트](../frontend/src/App.test.tsx)

## 2. 데스크톱 캘린더 조회와 캐시 이동

먼저 이전 데이터로 시작한 월 사전 로딩 요청을 지연시킨다. 사용자가 변경을 저장한 뒤 응답을 돌려주고, 해당 월을 열었을 때 저장 내용이 화면과 캐시에 남는지 확인하는 테스트를 작성한다. 현재 코드에서 테스트를 통과한 뒤 조회·사전 로딩·무효화를 캘린더 데이터 모듈로 옮긴다.

월·주 캐시 키, 주 시작 요일, 계정 전환, 사용자 시간대의 자정, 실패한 항목만 복구하는 동작을 다시 확인한다. 해당 테스트가 늦은 응답 차단 조건을 제거했을 때 실패하는지도 점검한다. [사전 로딩 응답 검사](../frontend/src/calendar/useCalendarData.ts#L262) · [계정 전환 테스트](../frontend/src/App.test.tsx)

## 3. 모바일 테스트와 빌드를 CI에 연결

모바일 패키지의 잠금 파일로 `npm ci`, `npm test`, `npm run build`를 실행하는 작업을 추가한다. 현재 CI는 `main` 푸시에서 실행된다. 화면 분리 전에 CI 실행 결과를 확인하고, 병합 전에도 같은 명령으로 변경 브랜치를 검증한다. 이 단계는 데스크톱 작업과 파일이 겹치지 않아 병행할 수 있다. [CI 워크플로](../.github/workflows/ci.yml) · [모바일 명령](../mobile-pwa/package.json)

## 4. 모바일 화면 이동

`SettingsView`를 먼저 옮긴다. 이어 로그인, 오늘, 캘린더를 한 화면씩 옮긴다. 앱 컴포넌트는 세션 복원과 탭 전환을 맡는다. `main.tsx`는 앱을 마운트한다.

이동 전후에 실제 브라우저에서 해시 주소로 탭 열기, 초기 로딩 오류 후 재시도, 로그아웃 후 다른 계정 로그인, 알림 클릭으로 탭 열기를 확인한다. 설정 화면은 권한 허용·거절, 구독 켜기·끄기, 테스트 알림도 확인한다. [앱 초기화](../mobile-pwa/src/App.tsx#L28) · [설정 화면](../mobile-pwa/src/screens/SettingsView.tsx#L9) · [알림 클릭 처리](../mobile-pwa/public/service-worker.js#L53)

## 5. Gemini 초안 파싱과 일정 검증 분리

공급자 응답 샘플을 테스트 fixture로 고정한다. 정상 초안, 잘못된 마일스톤이 섞인 초안, 날짜 제약 위반, 선호 요일 경고, `preferred_days: null`을 포함한다. 파싱과 일정 규칙을 분리한 뒤 응답 본문, 실패 코드, 경고를 기준선과 비교한다. Gemini 동의 확인과 사용자 확인 후 저장하는 흐름도 유지한다. 현재 파서의 `null` 예외 처리 개선은 별도로 결정한다. [현재 파서](../backend/app/services/ai_schedule_parser.py) · [서비스 테스트](../tests/test_ai_schedule_service.py) · [라우터 테스트](../tests/test_ai_schedule_routes.py)

## 6. 두 앱의 공통 API 응답 타입 도입

FastAPI OpenAPI와 실제 응답 샘플을 기준으로 월간 캘린더 한 엔드포인트부터 적용한다. 월간 최상위 마일스톤과 일별 마일스톤 요약은 서버에서 서로 다른 타입이다. 두 앱의 월간 API 호출부가 OpenAPI에서 파생한 타입을 실제로 사용하고, 중복된 월간 응답 타입 선언이 제거됐는지 확인한다. 두 앱이 동일한 응답 샘플을 읽고 테스트와 빌드를 통과하면 범위를 넓힌다.

로그인·갱신 계약은 별도로 비교한다. 서버는 `expires_at: null`을 허용하고 모바일은 양의 숫자를 요구한다. 데스크톱의 보안 저장소와 모바일의 탭 간 토큰 갱신 정책은 각 앱에서 유지한다. 이 차이를 다루는 테스트가 준비될 때까지 인증 타입 교체를 보류한다. [캘린더 스키마](../backend/app/schemas/calendar_schemas.py) · [인증 스키마](../backend/app/schemas/auth_schemas.py#L39) · [모바일 세션 검증](../mobile-pwa/src/api.ts#L22)

## 7. 캘린더 라우터 파일명 정리

`calender.py`를 `calendar.py`로 옮기고 `main.py`와 백엔드 README의 참조를 갱신한다. 이동 전후에 OpenAPI와 월간·주간·날짜 상세의 `200`·`401` JSON 응답을 비교한다. 요청마다 바뀌는 `request_id`는 응답 형식만 확인한다. 이동 뒤에 백엔드 앱이 정상적으로 로드되는지 확인한다. [라우터 등록](../backend/app/main.py#L100) · [라우터 테스트](../tests/test_app_routes.py#L711)

## 단계별 기록

각 단계를 독립적으로 검토할 수 있는 변경으로 올린다. PR에 기준 커밋, 비교 명령, 변경 전후 결과를 남긴다. 검증 결과는 `VERIFIED`, `NOT VERIFIED`, `INCONCLUSIVE` 중 하나로 기록한다. 필수 검증이 실패하거나 결과가 불확실하면 해당 변경을 병합하기 전에 원인을 확인한다.

## 구현 검증 기록

기준 커밋은 `e9146eb`이다. 기본 테스트는 백엔드 185개, 데스크톱 114개, 모바일 18개가 통과했고 두 앱의 프로덕션 빌드도 통과했다.

| 단계 | 구현 후 확인 |
|---|---|
| 1–2. 데스크톱 | 테스트 117개, 린트, 빌드 통과. 사전 로딩의 변경 번호 검사를 제거하면 새 회귀 테스트가 실패했다. 빌드된 화면의 오늘 패널을 Chromium에서 420×300, 640×480, 980×760으로 열어 배치·스크롤·완료 토글을 확인했다. |
| 3–4. 모바일 | 별도 복사본에서 잠금 파일 설치, 테스트 20개, 빌드 통과. Chromium에서 변경 전후 세션 복원, 해시 탐색, 로딩 재시도, 계정 전환, 알림 권한과 클릭 이동을 확인했다. 푸시 전송은 모의 처리했으며 호스팅된 GitHub Actions 실행은 남아 있다. |
| 5. Gemini | 백엔드 188개 통과. 기준 서비스와 공급자 응답 506건의 결과·예외·요청 인자를 비교했다. `preferred_days: null`의 기존 예외는 유지했다. |
| 6. API 타입 | 같은 FastAPI 월간 응답 샘플을 두 앱에서 검사했다. 두 HTTP 호출은 동일한 생성 타입을 사용한다. 서버 OpenAPI와 생성 결과의 일치 여부는 `python scripts/generate-calendar-contract.py --check`로 검사한다. |
| 7. 라우터 | 변경 전후 전체 OpenAPI와 캘린더 HTTP 응답 8건이 일치했다. 요청마다 생성되는 ID는 문자열 형식을 확인한 뒤 비교에서 제외했다. |

독립 검토에서 데스크톱의 월간 응답 타입과 캐시 상태 소유권을 지적했다. 두 호출부를 같은 생성 타입으로 맞추고 캐시의 변경·세션 참조를 훅 안에 둔 뒤 재검토를 마쳤다.
